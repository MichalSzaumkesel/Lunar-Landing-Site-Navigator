# Review A1: General Audit of the Whole App on Current Main

## Summary (Top 5 Findings)
- HIGH: `src/components/demo/demoSteps.ts:81-84` computes countdown from window start instead of cursor, displaying "Sun sets in 7 d 16 h" while the cursor sits at sunset.
- HIGH: `src/state/useUrlSync.ts:145-152` ignores `missionRules` changes in the subscription guard, so user mission rule edits are never persisted to the URL hash.
- HIGH: `index.html:1-28` lacks a Service Worker, causing offline reload tests (`docs/demo-script.md:12`) to fail with `ERR_INTERNET_DISCONNECTED`.
- HIGH: `src/components/share/ExportCardPngButton.tsx:37-47` queries hardcoded `#sky-views-${id}-tab-polar` that never matches React 19 `useId()`, breaking export tab detection.
- HIGH: `src/app/Panels.tsx:21` defaults to the Window Map tab, triggering immediate eager downloads of all 21 site datasets on initial launch.

## Findings (Ordered by Severity)

### 1. Demo countdown caption contradicts timeline cursor position
- **Severity**: HIGH
- **Location**: `src/components/demo/demoSteps.ts:81-84`
- **What is wrong**: In Step 3 (`step-3-sunset-countdown`), `run()` positions the time cursor exactly at the first sunset event (`store.setCursorH(sunsetH)`), but `formatStep3Caption()` calculates hours until sunset relative to `startMs` (the window start), yielding a countdown of several days rather than zero.
- **Evidence / Failing Scenario**: Trigger "Demo" in the top bar. When Step 3 begins, the cursor jumps to the sunset line, but the caption reads: *"Artemis candidate region: Sun sets in 7 d 16 h."* Jurors see an active cursor at sunset with a conflicting 7-day countdown.
- **Suggested Fix**:
  ```ts
  const cursorMs = startMs + (store.getState().cursorH * HOUR_MS)
  const hoursUntil = Math.max(0, (firstSunset.ms - cursorMs) / HOUR_MS)
  ```
  Or jump the cursor to 12 hours before sunset (`Math.max(0, sunsetH - 12)`) so the remaining time visibly aligns with the timeline position.

### 2. Store subscription in URL sync drops mission rules updates
- **Severity**: HIGH
- **Location**: `src/state/useUrlSync.ts:145-152`
- **What is wrong**: The change-detection guard in `useUrlSync` only checks `state.mode`, `observerHeightM`, `speedHPerSec`, and `scenarios`. It omits `missionRules`, returning early before serializing updates.
- **Evidence / Failing Scenario**: In Advanced mode, modify mission parameters in the Window Map or Tools (e.g. change mission duration to 336 h or required sunlit to 80%). Copy the share URL or reload the browser. The URL hash is never updated with the new rule parameters, and all changes revert to defaults on reload.
- **Suggested Fix**:
  ```ts
  if (
    state.mode === lastMode &&
    state.observerHeightM === lastHeight &&
    state.speedHPerSec === lastSpeed &&
    state.scenarios === lastScenarios &&
    state.missionRules === lastRules
  ) {
    return
  }
  ```

### 3. Missing Service Worker prevents offline reload claimed in docs
- **Severity**: HIGH
- **Location**: `index.html:1-28` / `docs/demo-script.md:12`
- **What is wrong**: `CLAUDE.md:58` states "No backend. The site works offline once loaded", and `docs/demo-script.md:12` instructs presenters: *"Offline test: switch DevTools to Offline, reload, and confirm the scenario still renders."* However, no Service Worker is registered in `web/`.
- **Evidence / Failing Scenario**: Presenter or jury toggles DevTools Network to "Offline" and reloads (`F5` / `Ctrl+R`). The browser immediately displays `ERR_INTERNET_DISCONNECTED` because static HTML/JS assets cannot load without a service worker cache.
- **Suggested Fix**: Either register a minimal service worker caching the Vite build assets and prefetched data, or update `docs/demo-script.md` and `README.md` to remove the reload instruction and state that offline capability applies only to in-session navigation without full reload.
- **DECISION**: Lead must decide whether to introduce a service worker or adjust demo documentation.

### 4. Card PNG export queries non-existent tab ID generated by useId()
- **Severity**: HIGH
- **Location**: `src/components/share/ExportCardPngButton.tsx:37-47`
- **What is wrong**: `ExportCardPngButton` checks whether the Polar view is active by querying `#sky-views-${scenario.id}-tab-polar`. In `SkyViews.tsx:84`, the tab IDs are generated using React's `useId()` (e.g. `:r0:-tab-polar`), so the query selector is always null.
- **Evidence / Failing Scenario**: Because `#sky-views-...` is never found and `anyTab` evaluates to null, `!anyTab` defaults to `true`. When a user switches to the 3D or Panorama tab and clicks "Save card as PNG", `svg.sky__svg` is null because `PolarPanel` is unmounted. The canvas export downloads a PNG containing an empty placeholder "Sky plot" rectangle instead of disabling the button.
- **Suggested Fix**: Query the tab using an attribute selector matching the ID suffix:
  ```ts
  const polarTab = document.querySelector<HTMLButtonElement>(`[role="tab"][id$="-tab-polar"]`)
  ```
  Or pass the active view state from `SkyViews` down to `ExportCardPngButton`.

### 5. Default Window Map panel triggers eager load of all 21 site datasets
- **Severity**: HIGH
- **Location**: `src/app/Panels.tsx:21` and `src/components/finder/WindowMap.tsx:116-135`
- **What is wrong**: The lower panels section defaults to `active = 'window-map'`. On initial page load, `WindowMap` mounts and immediately initiates sequential batch-loading of all 21 sites (`data/horizon/*.json` and `data/ephem/*.json`) and runs two heavy worker calculations.
- **Evidence / Failing Scenario**: Opening the landing page triggers over 40 HTTP requests and launches worker threads in the background, conflicting with the rule: *"data files load lazily per site; the first screen needs no heavy computation."*
- **Suggested Fix**: Set the default active panel in `Panels.tsx` to a lighter panel (such as `moon-map` or `sites`), or defer the 21-site fetch until the user explicitly expands the Window Map.
- **DECISION**: Lead to approve changing default active panel in `Panels.tsx`.

### 6. Production build produces 648 kB SurfaceView chunk exceeding Vite limit
- **Severity**: MEDIUM
- **Location**: `vite.config.ts:58-65`
- **What is wrong**: `npm run build` outputs: `dist/assets/SurfaceView-CMG_4DSf.js 647.97 kB` and throws warning `(!) Some chunks are larger than 500 kB after minification`.
- **Evidence / Failing Scenario**: Run `npm run build`. Vite flags `SurfaceView` because Three.js is bundled directly into it rather than into a dedicated vendor chunk.
- **Suggested Fix**: Add `build.chunkSizeWarningLimit: 750` or configure Rollup `manualChunks` in `vite.config.ts`:
  ```ts
  build: {
    chunkSizeWarningLimit: 750,
    rollupOptions: {
      output: {
        manualChunks: { three: ['three'] }
      }
    }
  }
  ```

### 7. CSP meta tag is disabled in development mode
- **Severity**: MEDIUM
- **Location**: `vite.config.ts:36`
- **What is wrong**: `cspPlugin` specifies `apply: 'build'`. Consequently, the Content Security Policy meta tag is absent when running `npm run dev`.
- **Evidence / Failing Scenario**: Developers working on local features cannot observe CSP violations (such as worker blob permissions or unsafe inline style rules) until after running a full production build and preview.
- **Suggested Fix**: Remove `apply: 'build'` or inject CSP headers into the Vite development server via `server.headers`.

### 8. Missing HTTP security headers in production hosting configuration
- **Severity**: MEDIUM
- **Location**: `index.html:1-28` / `vite.config.ts`
- **What is wrong**: CSP is delivered strictly through a `<meta>` tag in `index.html`. Meta tags cannot set `frame-ancestors`, `X-Frame-Options`, `X-Content-Type-Options: nosniff`, or `Referrer-Policy`.
- **Evidence / Failing Scenario**: Security evaluation of the static build reveals missing clickjacking protection and missing MIME sniffing prevention headers.
- **Suggested Fix**: Provide a static headers configuration file (e.g., `public/_headers` for Cloudflare Pages / Vercel configuration) to supply standard HTTP response security headers.

### 9. Non-demo sites show unhelpful dead-end message in 3D tab
- **Severity**: MEDIUM
- **Location**: `src/viz3d/SurfaceView.tsx:852-867`
- **What is wrong**: When viewing any of the 18 non-demo sites (e.g. Apollo 12, Chandrayaan-3, SLIM), selecting the "3D" tab displays: *"No terrain for this site"* with a disabled *"Find sunniest spot"* button, without guidance on what to do next.
- **Evidence / Failing Scenario**: A user exploring various landing sites switches to 3D view and encounters a dead-end UI, violating the guideline: *"Every view has four states: loading, empty or outside data range, error (plain language, what to do next)"*.
- **Suggested Fix**: Update the empty message: *"3D terrain is available for demo sites (Apollo 11, South Pole, Artemis candidate region). Switch to Polar or Panorama view, or select a demo site from the library."*

### 11. Live preset dates diverge from pitch documentation statistics
- **Severity**: MEDIUM
- **Location**: `src/config/presets.ts:25-27` vs `docs/pitch.md:34-39`
- **What is wrong**: `presets.ts` sets `DEFAULT_START_UTC = '2027-10-06T00:00:00Z'` (showing 52% Sun visible at South Pole), while `docs/pitch.md` quotes January 2027 figures (6.8% to 94.0%).
- **Evidence / Failing Scenario**: If a presenter cites figures from `docs/pitch.md` during a live demo, the values will contradict the numbers rendered on the screen.
- **Suggested Fix**: Ensure `docs/demo-script.md` explicitly warns presenters to read live numbers directly from scenario cards, and align `docs/pitch.md` references.

### 12. Generic tooltips on DataBadges lack specific dataset context
- **Severity**: LOW
- **Location**: `src/components/badges/DataBadges.tsx:16-32`
- **What is wrong**: Badges display generic strings (*"Real-based data with a known simplification"*) regardless of whether the approximation relates to coordinates, terrain bounds, or illumination.
- **Evidence / Failing Scenario**: Users viewing an "Approximate" badge on custom coordinates cannot determine which component is simplified.

### 13. Pure lib modules contain relative imports with .ts extensions
- **Severity**: LOW
- **Location**: `src/lib/metrics.ts:6-8`, `src/lib/ephem.ts:1-2`
- **What is wrong**: Several modules import with explicit `.ts` extensions (`import ... from './types.ts'`), violating `tasks/_common.md` rule: *"Relative imports without a file extension, like src/lib/loader.ts"*.
- **Evidence / Failing Scenario**: Inconsistent import styling across lib modules.
- **Suggested Fix**: Strip `.ts` extensions from imports in `src/lib/metrics.ts` and `src/lib/ephem.ts`.

### 14. Badge font size is 12px while body text guideline requires 14px
- **Severity**: LOW
- **Location**: `src/app/theme.css:323` and `src/components/sky/sky.css:371`
- **What is wrong**: `.badge` styles use `font-size: 0.75rem` (12px). While SVG minimum is 12px, body text minimum is 14px in `tasks/RULES-quality.md`.
- **Evidence / Failing Scenario**: Badges may be difficult to read on lower-resolution projector displays during the jury presentation.
- **Suggested Fix**: Increase badge font size to `0.8125rem` (13px) or `0.875rem` (14px).

### 15. Earth loupe target is out of view for equatorial landing sites
- **Severity**: LOW
- **Location**: `src/components/sky/Loupe.tsx:49-59`
- **What is wrong**: The Loupe magnification window is constrained to elevation −1° to +5°. For equatorial sites like Apollo 11, Earth sits at ~60° elevation, so the Loupe display is always blank with a text notice.
- **Evidence / Failing Scenario**: Clicking "Earth" in Apollo 11's loupe displays an empty grey window with text *"Earth is outside the magnified window (elevation 59.8 deg)"*.
- **Suggested Fix**: Disable the Earth toggle or add a visual indicator when Earth elevation exceeds +5°.
